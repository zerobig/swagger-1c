## [2.1.0] - 2026-XX-XX

Релиз добавляет поддержку JSON-RPC 2.0 через стандарт OpenRPC 1.3.2. Обратная совместимость сохранена: HTTP-сервисы без явного указания `Протокол = "json-rpc"` продолжают работать как раньше, `swagger.json` не меняется.

### Добавлено

#### JSON-RPC (OpenRPC 1.3.2)

- Настройка `Протокол` в `ПолучитьОбщиеНастройки()` модуля `<Имя>Описание`. Значения: `"http"` (по умолчанию) или `"json-rpc"`. Если поля нет — считается `"http"`, поведение не меняется.
- Функция `Swag_Сборщик.СобратьМодельOpenRPC(Настройки)` собирает документ OpenRPC из HTTP-сервисов с `Протокол = "json-rpc"`. Функция `Swag_Сборщик.ПараметрыHTTPМетода(ИмяСервиса, ИмяМетода)` разрешает пару (имя сервиса, имя метода) в `{URL, HTTPМетод}` через метаданные. Используется `Swag_ZodАдаптер` для поиска операции в модели без зависимости от `operationId`.
- Функции `Swag_АдаптерСовместимости`:
  - `ПреобразоватьМетодJSONRPC` — метод `<Имя>Описание` в OpenRPC-метод.
  - `ПреобразоватьJSONRPCПараметр` — параметр в формат OpenRPC.
  - `СхемаИзJSONRPCПараметра` — построение JSON Schema из параметра.
  - `ПреобразоватьJSONRPCРезультат` — ответ 200 в поле `result` OpenRPC.
  - `СхемаВФорматOpenRPC` — приведение схемы к формату JSON Schema (внутреннее имя `ref`, сериализатор превращает в `$ref`).
- `Swag_Запросы.СформироватьJsonRpc` теперь собирает реальный OpenRPC-документ из модели. Статический пример оставлен как fallback для случая, когда в конфигурации нет JSON-RPC сервисов или сборка упала.
- Внутреннее поле `paramStructure: "by-name"` эмитится для методов с параметрами. Это соответствует тому, как `<Имя>Описание` создаёт параметры через `.ПараметрЗапроса()` — именованные, а не позиционные.
- HTTP-метод `GET /swagger/json-rpc.json` отдаёт OpenRPC-документ. Совместим с предыдущими версиями по URL; изменилось содержимое (теперь это реальная модель, а не статический пример).

#### Демонстрационный сервис JSON-RPC

- HTTP-сервис `Demo_RPC` с обработчиком `RPC_POST`, реализующий JSON-RPC 2.0: одиночные запросы, батч-запросы, уведомления (notification), стандартные коды ошибок JSON-RPC (-32700, -32600, -32601, -32602, -32603) и серверные коды (-32001).
- Демонстрационные методы: `echo`, `sum`, `time.now`, `products.list`, `products.get`.
- Модуль `Demo_RPCОписание` — описание сервиса в формате OpenRPC.

#### Утилиты

- `Swag_Запросы.УбратьИмяСервисаИзURL(БазовыйURL)` — универсальное вырезание последнего сегмента из URL. Используется при формировании `servers[].url` в JSON-RPC и swagger-документах.
- `Swag_Запросы.ПолучитьБазовыйURLСПортом` переработан: корректно работает, когда `Запрос.БазовыйURL` уже содержит порт (в предыдущих версиях порт мог задваиваться: `http://host:8081:8081`). Заголовок `Host` читается без учёта регистра.

### Изменено

- `Swag_Запросы.ПолучитьJsonRpcFileGET` использует `УбратьИмяСервисаИзURL` вместо жёсткой замены `"/swagger"`. Это работает при любом имени служебного HTTP-сервиса документации.
- В `servers[].url` JSON-RPC-документа добавляется имя API-сервиса: `{базовый_URL}/{ИмяСервиса}/{КорневойURL}{Шаблон}`. Ранее имя сервиса отсутствовало, и URL не был рабочим.
- Колонка `Сервис` в отчёте `Swag_Сборщик.ДиагностикаОписаний()` переименована в `URL`. Причина: колонка содержит не имя сервиса, а путь операции в модели (`paths./api/create.post`). Новая колонка `URL` точнее отражает содержимое. Тесты обновлены.

### Исправлено

- `Swag_Запросы.ПолучитьБазовыйURLСПортом` не задваивает порт, если `Запрос.БазовыйURL` уже содержит порт.
- `Swag_Сборщик.ДобавитьJSONRPCSервис` использует `ЗаписатьОшибкуСервиса` (локальная функция `Swag_Сборщик`). Ранее вызывалась несуществующая `ЗаписатьОшибкуМетода` из другого модуля.
- `Swag_АдаптерСовместимости.СхемаВФорматOpenRPC` использует внутреннее имя `ref` (не `$ref`). Сериализатор превращает `ref` в `$ref` при выводе JSON. Ранее адаптер создавал `$ref` напрямую, что нарушало единый паттерн библиотеки.

### Ограничения

- HTTP-сервис с `Протокол = "json-rpc"` должен иметь ровно один шаблон URL. Если шаблонов несколько — сервис пропускается с записью в журнал регистрации (код ошибки в журнале содержит имя сервиса и причину).
- Имена JSON-RPC методов должны быть уникальны в пределах конфигурации. При дубликате второй метод пропускается с записью в журнал.
- Параметры JSON-RPC методов создаются через `.ПараметрЗапроса()`. Отдельный метод `.ПараметрJSONRPC()` не вводился, потому что сервис целиком помечен как `"json-rpc"` — разделение параметров по протоколу внутри одного сервиса не поддерживается.
- Позиционные параметры JSON-RPC (`params` как массив) не поддерживаются. Все параметры описываются как именованные (`params` как объект).
- Описание ошибок JSON-RPC (`errors` в методе OpenRPC) не эмитится. Клиент ориентируется на стандартные коды из спецификации JSON-RPC 2.0.
- Функция `ДиагностикаОписаний` собирает только OpenAPI-модель. JSON-RPC сервисы в неё не попадают (см. BACKLOG).

### Совместимость

- HTTP-сервисы без `Протокол = "json-rpc"` не затронуты. `swagger.json` формируется по прежним правилам.
- Существующие модули `<Имя>Описание` не требуют изменений.
- `SwaggerОбщиеНастройки` не менялся. Все настройки прежние.

## [2.0.0] - 31.10.2026

Релиз объединяет два независимых улучшения: генератор OpenAPI 3.1 на базе собственной модели и опциональную валидацию запросов через библиотеку zod-1c.

Обратная совместимость сохранена. По умолчанию используется прежний генератор OpenAPI 3.0.0, текущие модули `<Имя>Описание` не требуют изменений.

### Добавлено

#### Новый генератор OpenAPI 3.1

- Модель OpenAPI 3.1: общий модуль `Swag_Модель`, обработки `Swag_Схема` и `Swag_Операция`. Схемы, операции, параметры, тела запросов, ответы, security-схемы описываются через fluent-интерфейс и валидируются перед сериализацией.
- Сборщик `Swag_Сборщик`, который сканирует метаданные HTTP-сервисов и собирает модель из существующих модулей `<Имя>Описание`.
- Адаптер совместимости `Swag_АдаптерСовместимости`, который преобразует результаты существующих функций `ПолучитьОписаниеHTTPСервиса` и `ПолучитьОбъектыHTTPСервиса` в модель OpenAPI 3.1.
- Сериализатор `Swag_СериализаторOpenAPI`. Выдаёт валидный JSON по стандарту OpenAPI 3.1.
- Настройка `РежимГенератора` в `SwaggerОбщиеНастройки` с тремя значениями: `"Выкл"` (по умолчанию, старый генератор), `"Мягкий"` (новый генератор, предупреждения не блокируют JSON), `"Строгий"` (новый генератор, любая ошибка ведёт к откату на старый генератор).

#### Диагностика описаний

- Функция `Swag_Сборщик.ДиагностикаОписаний()` возвращает таблицу замечаний по всем описаниям HTTP-сервисов.
- HTTP-метод `GET /swagger/diagnostics` для получения отчёта в JSON и `GET /swagger/diagnostics?format=csv` для выгрузки в CSV.
- Коды замечаний в отчёте: критичные (`*_MISSING`, `*_INVALID`) отделены от предупреждений (`*_WARN`), что позволяет использовать мягкий режим при миграции.

#### Валидация запросов через zod-1c

- Общий модуль `Swag_ZodАдаптер`, преобразующий модель OpenAPI в схемы zod-1c и валидирующий входящие запросы (`ПроверитьЗапрос`, `ПроверитьЗапросПоМодели`) и исходящие ответы (`ПроверитьОтветПоМодели`).
- Поиск операции в модели по паре `(URL, HTTP-метод)`, а не по `operationId`. Это делает валидацию независимой от того, как пользователь назвал операцию.
- Проверка наличия установленного `zod-1c` (`Swag_ZodАдаптер.ЕстьZod`). При отсутствии библиотеки генерация спецификации работает без изменений, а функции адаптера выбрасывают понятное исключение при вызове.
- Динамическая загрузка модуля `Zod` через `Вычислить` (как в БСП), чтобы `Swag_ZodАдаптер` компилировался даже при отсутствии `zod-1c`.

#### Демонстрационный сервис

- HTTP-сервис `Demo_Products` с описанием `Demo_ProductsОписание`. Показывает правильное оформление API: параметры, тела запросов, ответы всех кодов, переиспользование схем через `$ref`, валидацию через `Swag_ZodАдаптер`.

#### Настройки

- Общий модуль `SwaggerОбщиеНастройки` с полями `РежимГенератора`, `Title`, `Version`, `BaseURL`, `UseBasicAuth`, `МассивНеотображаемыхСервисов`. Настройки читаются при сборке модели. При отсутствии модуля используются значения по умолчанию.
- Поддержка отдельного модуля `SwaggerОбщиеНастройкиПользователя` для случаев, когда настройки нужно отделить от кода библиотеки.

#### Утилиты

- `Swag_ОбработкаHTTP.ОтветJSON(Данные, Код)` для формирования JSON-ответа. Функция `Swag_Сборщик.ПараметрыHTTPМетода(ИмяСервиса, ИмяМетода)`, возвращающая пару `(URL, HTTP-метод)` по имени метода из описания.

### Изменено

- Служебный HTTP-сервис `Swag_Сервис` дополнен шаблоном `/swagger/diagnostics`. `Swag_Запросы.СформироватьБазовыйSwaggerJson` умеет переключаться между старым и новым генератором по настройке `РежимГенератора`.
- В `Swag_Сборщик.СобратьМодель` добавлена поддержка мягкого режима: неполные описания (пустые `responses`) дают код `OPERATION_RESPONSES_EMPTY_WARN` вместо `OPERATION_RESPONSES_MISSING`.
- Тесты и тестовые сервисы перенесены из отдельного расширения в основное. Изменниебыло сделано для облегчения освоения функционала новыми пользователями.

### Исправлено

- `Swag_АдаптерСовместимости` не удаляет кириллицу из `operationId`. Ранее санитизация ломала поиск операций в `Swag_ZodАдаптер`.
- `Swag_ZodАдаптер.ПроверитьТелоЗапроса` корректно обрабатывает тело запроса, прочитанное как `Соответствие` (а не только как `Структура`).

### Ограничения

- Режим `СовместимостьС30` в сериализаторе реализован частично: конвертирует `nullable` и `exclusiveMinimum`, но не подменяет значение поля `openapi` на `"3.0.3"`. До полной реализации режим не рекомендуется к использованию.
- В общих модулях 1С нет переменных модуля, поэтому модель OpenAPI собирается при каждом запросе. Для оптимизации предусмотрена функция `ПроверитьЗапросПоМодели` с передачей готовой модели снаружи.

### Миграция

Переход на новый генератор опционален. Существующие пользователи не требуют никаких действий: по умолчанию работает прежний генератор OpenAPI 3.0.0.

Пошаговая инструкция - в [MIGRATION.md](MIGRATION.md).
